每月處理 7000 億 Token：AT&T 如何用 530 張 GPU 打造電信專屬 AI

AT&T 透過 Microsoft Foundry 與 530 張混合 GPU 算力，打造每月處理數千億 Token 的電信專屬 AI 模型。

700B+PHI-4 每月處理 TOKEN 數
430部署之 AMD MI300X GPU 數量
發生了什麼

通用大模型往往缺乏電信網路、標準與營運的專業知識。為了打破這個瓶頸，電信巨頭 AT&T 推出新一代 Open Telco（OTel2.0）模型，透過 Microsoft Foundry Managed Compute 平台，靈活調度多款開源模型與硬體架構，支援萬億級 Token 的大規模數據處理。

在這次部署中，AT&T 採用了多開源模型策略，包含 Hugging Face 社群中的 Phi-4、OSS-120B 以及 Gemma 4。其中 Phi-4 在數據準備與合成數據生成階段，每月處理超過 7000 億個 Token。底層硬體則動用了約 530 張 GPU，包含 430 張 AMD Instinct MI300X GPU 以及 NVIDIA GPU，成功將模型與硬體的部署時間從數週縮短至數小時。

為什麼重要

這項實踐展示了企業級 AI 發展的關鍵轉折：企業不再需要被單一模型或單一晶片供應商綁架。過去團隊必須自行維護龐大的硬體基礎設施與營運負擔，而現在透過託管計算平台，能像調酒一樣，依據不同任務混搭最適化的模型與算力。

例如處理高階推理任務時調用 OSS 120B，進行數據準備時使用 Phi-4，而開發工作流則交給 Gemma 4。配合跨晶片架構的異質算力，企業能在控管成本與維持效能之間取得最佳平衡，讓大規模領域專用 AI 的開發變得極具可行性。

值得追蹤的後續

雖然異質算力與多模型組合帶來了極高的彈性，但不同 GPU 架構之間的軟體優化程度、吞吐量瓶頸以及跨架構調度的維護成本，仍是大規模營運時必須面臨的實務考驗。隨著 AT&T 將 OTel 模型回饋給社群，這套開放架構在實際電信場景中的長期總體持有成本與維護複雜度，將是未來技術評估的核心指標。

這對我們意味著什麼

可以想像，當我們在思考廠區設備報修或 IT Helpdesk 等內部 AI 應用時，不一定要強制全公司統一採用單一昂貴的大模型。我們可以試著將任務拆解，讓較輕量、成本較低的模型去處理日常假勤查詢或格式化數據整理，而將複雜的推理任務留給高階模型。

在硬體與平台規劃上，同樣可以思考如何透過靈活的架構分配算力資源。透過任務分流與適度搭配不同規格的硬體，能夠在滿足各部門回應速度需求的同時，精準控制整體營運成本。

試播兩人沒事、十五人同時開工卻卡死：AI 自動寫程式的防護牆調校課

15 位工程師同時使用 Claude Code 卻導致系統卡死，原因出自預設防護牆每 50 字元就檢查一次。

15 人同時上線引發 THROTTLINGEXCEPTION 的開發者人數
5,000 字元工程師平均每個函式產生的程式碼長度
50 字元預設觸發防護牆評估的串流間隔
痛點

一家團隊將 Amazon Bedrock 上的 Claude Code 推廣給 15 位工程師使用。雖然兩人的小規模測試非常順利，但當 15 人同時展開寫程式任務時，系統卻頻繁傳回 ThrottlingException 錯誤，程式碼生成甚至在中途直接卡死。

具體做法

問題的根源在於檢查機制太過頻繁。工程師平均每編寫一個函式就會產生約 5,000 個字元，但在預設的串流設定下，系統每產出 50 個字元就會觸發一次防護牆評估，導致 API 請求量瞬間暴增。

導入程式碼輔助工具時，防護牆必須防範提示詞攻擊、遮蔽金鑰與個人資料，並攔截違規內容。要維持系統順暢，關鍵在於重新設定串流評估的字元間隔與吞吐量配置，避免過度頻繁的檢測干擾開發流程。

成效或注意事項

如果沒有針對團隊併發需求進行容量規劃與參數調整，防護牆可能帶來 API 限制、成本上升與延遲增加等問題。透過精準調整串流檢查頻率，能在確保金鑰防護與安全審查的同時，維持多位開發者順暢並行的作業體驗。
